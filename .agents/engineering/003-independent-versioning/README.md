# 003 独立版本号

- 状态：done（用户 2026-11-20 确认版本组；结论已合入 `core-product` 规约「工程约定」）
- 关联规格：无（发布流程见 `RELEASING.md`）

## 目标与范围

以前的做法是 21 个包每次一起升版本号。比如 0.8.3 只改了 image-zoom 和 nagi，也把全部包重发了一遍。改成谁改了谁发版，减少无意义的发版噪音。

## 现状

- 发布脚本本身已经支持独立版本：它只发布「npm 上还没有这个版本」的包，其余跳过。
- 同号是约定出来的：CHANGELOG 开头写着全部包共用一个版本号。
- 结构上的耦合：
  - 插件对 `kawapress` 的 peer 依赖写的是 `workspace:^`，发布后变成 `^0.8.3`。在 0.x 阶段，这只匹配 `>=0.8.3 <0.9.0`。
  - `kawapress` 依赖 `preset-nagi`，`preset-nagi` 又依赖 12 个内置插件。所以核心每升一个 minor，这一串都得跟着发。

## 技术方案

1. 版本组：
   - `kawapress`、`create-kawapress`、`preset-nagi` 保持同号，一起发版。它们互相依赖，实际上是一个产品。
   - 其余插件各自独立发版。
2. peer 范围：插件对 `kawapress` 的 peer 改成 `workspace:>=0.8.3 <0.10.0`。pnpm 发布时去掉 `workspace:` 前缀，tarball 校验（`expectedWorkspaceRange`）已支持。只有插件用到新核心 API 时才提高下限。
3. 新插件从 `0.1.0` 开始独立计版本（npm 占位用 `0.0.1`）。
4. 更新日志：只保留根目录中英文两份（npm 包页面不展示分包 CHANGELOG，维护 20 多份收益太低）。每次发布一节，标题是日期加主要包和版本，节首列出本次各包版本，插件条目注明包名。
5. `release:prepare` 增加检查（`scripts/release/versioning.mjs`）：
   - 核心版本组必须一起升、同一个版本，否则报错。
   - 核心新版本超出某插件 peer 范围时报错。
   - 自上一个发布 tag 以来改过发布文件（不含测试）、版本号却没升的包，列出来提醒。
6. 同步改 `RELEASING.md` 的「版本号怎么选」和「发布说明」两节。

## 风险与回滚

peer 范围放宽之后，可能出现插件实际上和新核心不兼容、却没有报 peer 警告的情况。CI 里所有插件都和当前核心一起测试，可以兜住仓库内的组合。如果要回滚，把 peer 改回 `workspace:^` 即可。

## 验证

- `pnpm release:dry` 只改一个插件的版本号时，只有这个包被标为待发布。
- 打出来的 tarball 里，peer 范围是预期的值。
